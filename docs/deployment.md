# Релизный архив и установка на VPS

Workflow `.github/workflows/ci-release.yml` выполняет проверки для `push` и `pull_request` в `main`, а также при ручном запуске. Архив создаётся только для `push` в `main` и `workflow_dispatch`; pull request, в том числе из fork, выполняет проверки без production-секретов и ничего не публикует.

## Получение артефакта

Для ручного запуска откройте в GitHub вкладку **Actions**, выберите **Checks and release archive**, нажмите **Run workflow** и выберите нужную ветку или commit. После успешного job скачайте артефакт `grelqa-<полный commit SHA>-linux-x64` внизу страницы запуска. GitHub отдаёт ZIP-обёртку, внутри находятся:

- `grelqa-<короткий SHA>-linux-x64.tar.gz`;
- файл `.sha256` для проверки архива;
- `.metadata.txt` с полным commit SHA, версиями Node.js, ОС и архитектурой сборки.

Срок хранения артефакта — 14 дней. Workflow не создаёт GitHub Release, не подключается к VPS и не выполняет deployment.

Проверьте checksum и распакуйте архив, например:

```bash
sha256sum --check grelqa-*-linux-x64.tar.gz.sha256
sudo mkdir -p /srv/grelqa-releases
sudo tar -xzf grelqa-*-linux-x64.tar.gz -C /srv/grelqa-releases
```

Внутренний каталог архива можно сделать целью управляемой оператором ссылки `/srv/grelqa`. Не удаляйте предыдущий релиз, пока новый не проверен. Постоянные данные не должны лежать ни в каталоге версии, ни внутри этой ссылки.

## Совместимость

Архив собирается на GitHub-hosted `ubuntu-24.04` x86-64 для Ubuntu 24.04 x86-64. В нём находятся GNU/Linux x64 нативные модули libsql/SQLite и Argon2. На VPS требуется Node.js **26.13.0** из `.nvmrc`; npm для установки релиза не нужен. Не переносите этот архив на Alpine/musl, ARM или другую ОС и не заменяйте Node.js другой major/minor-версией без новой проверки.

## Runtime-окружение

Секреты задаются только на VPS через закрытый `EnvironmentFile` или менеджер секретов. Не кладите настоящий `.env` в каталог релиза. Для production нужны:

- `NODE_ENV=production`;
- `DATABASE_URL=file:/абсолютный/путь/grelqa.db` — одна локальная SQLite вне релиза;
- `APP_URL=https://домен` и `SITE_URL=https://домен`;
- случайный `SESSION_SECRET` длиной не менее 32 символов;
- `MAIL_MODE=smtp`, `MAIL_FROM`, `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE` и согласованная пара `SMTP_USER`/`SMTP_PASSWORD`, если SMTP требует авторизацию;
- `EXPORT_CACHE_DIRECTORY=/абсолютный/приватный/путь/exports`;
- необязательный `SOURCE_CODE_URL` по правилам из README.

`MAIL_DIRECTORY` используется только development-режимом; production запрещает локальные письма. Пользователь службы должен иметь права на каталог SQLite, включая создаваемые рядом WAL/SHM, и на приватный каталог ZIP-кеша.

В текущем коде нет переменных `NEXT_PUBLIC_*` и нет интеграции SmartCaptcha. Поэтому GitHub Variables для клиентского ключа сейчас не нужны, а секрет SmartCaptcha workflow не получает. Если клиентская интеграция будет добавлена, её публичный `NEXT_PUBLIC_*` ключ потребуется передавать именно на шаг `npm run build`: такие значения встраиваются в браузерный bundle. Серверный секрет SmartCaptcha, SMTP-пароль и `SESSION_SECRET` должны оставаться только runtime-настройками VPS.

## Первый запуск

Остановите сервер и обработчик расписания. Перед миграциями сделайте согласованную резервную копию рабочей SQLite: безопаснее использовать SQLite backup при остановленных процессах; нельзя копировать только файл `.db` у работающей базы или вручную отделять его от WAL/SHM. Затем из корня распакованного релиза выполните:

```bash
export DATABASE_URL=file:/srv/grelqa-data/grelqa.db
bin/grelqa migrate
NODE_ENV=production HOSTNAME=127.0.0.1 PORT=3000 bin/grelqa server
```

Приложение не запускает seed и не добавляет демонстрационные записи автоматически. Для обработки наступивших переходов тот же пользователь и то же `DATABASE_URL` запускает:

```bash
bin/grelqa schedule
```

`deploy/systemd/` содержит пример oneshot service и timer. Оператор должен проверить пути к релизу, `EnvironmentFile`, пользователя, права и `ReadWritePaths`, затем сам установить/включить unit. Архив и workflow системные службы не меняют. Для очистки старого публичного ZIP-кеша доступна команда `bin/grelqa exports-clean`; `bin/grelqa help` показывает упакованные административные команды. Перенос актуальной старой базы в отдельный файл доступен как `bin/grelqa rebuild -- --output /absolute/new.db` и требует выполнения условий раздела о rebuild в README.

После миграции схема базы может оказаться несовместима со старым приложением. Возврат ссылки `/srv/grelqa` на прежний каталог не является полноценным откатом: для него может потребоваться восстановление сделанной до миграции резервной копии. Никогда не запускайте две версии приложения одновременно на одной SQLite во время миграции или переключения.

## Что проверяет workflow

После lint, typecheck, production build и всех существующих тестовых наборов workflow собирает архив, распаковывает его в отдельный временный каталог и, не выполняя там `npm install`, проверяет:

- миграции на новой временной SQLite;
- загрузку нативного Argon2;
- один проход обработчика расписания;
- наличие административных команд;
- запуск production standalone-сервера и доступность страницы и файла из `.next/static`.

Smoke-тест использует только временные каталоги, тестовый session secret и недоступный локальный SMTP endpoint. Он не обращается к рабочей базе или внешней почте. Полную совместимость с конкретным VPS, реальную SMTP-доставку, reverse proxy, права systemd и резервное копирование подтверждает оператор при установке.
