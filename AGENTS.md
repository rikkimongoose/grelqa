# Работа с Grelqa

## Требования и границы

Сначала прочитайте `docs/grelqa_rules_and_spec.md`. Различайте принятые решения, исходные правила, предложения и открытые вопросы. Предложения не являются согласованными требованиями. Не изменяйте документ требований без запроса пользователя.

Текущий шаг — SQLite/Drizzle, аутентификация, публичное чтение и приватные «Мои работы», подача, редактирование и снятие. SQLite и модель согласованы запросом пользователя; остальные предложения из ТЗ не принимаются автоматически. Регистрация, письма и сессии согласованы текущим запросом. Подача и редактирование согласованы текущим запросом. Первый тур голосования и отдельный черновик бюллетеня согласованы запросом от 1 ноября 2026. Закрытие первого тура, снятия за неголосование, результаты и состав финала согласованы запросом от 1 ноября 2026. Финальные бюллетени согласованы отдельным текущим запросом. Окончательный подсчёт, финальные санкции и раскрытие публичных имён согласованы текущим запросом. Веб-управление и модерация согласованы текущим запросом. Внешний однократный обработчик расписания разрешён текущим запросом; таймеры в Next.js и автоматическую установку служб не добавляйте; не добавляйте черновики рассказов и автосохранение. Не создавайте фиктивно работающие формы. Сохраняйте оформление, документы и настройки Git. Коммиты, push и развёртывание требуют отдельного запроса. PostgreSQL пока вне объёма.

## Устройство

- `src/app/layout.tsx`, `globals.css`, `not-found.tsx` — общий каркас и оформление.
- `src/app/page.tsx`, `src/app/contests/[slug]/page.tsx` — серверные динамические страницы; читают SQLite на запросе, не фиксируют данные в сборке.
- `src/components/stage-badge.tsx`, `src/lib/contests.ts` — подписи/типы этапов и форматирование МСК. Не размещайте здесь секретные данные и seed.
- `src/db/schema.ts` — Drizzle-схема и выводимые из неё типы. Конкурсные таблицы: users, contests, contest_themes, participations, contest_groups, stories, story_rounds, ballots, ballot_entries.
- `src/db/connection.ts` — низкоуровневое подключение для сервера и CLI; только локальные `file:` URL, FK включены на каждом соединении.
- `src/db/index.ts` — серверное соединение с `server-only`.
- `src/db/public-contests.ts` — `server-only`, белый список публичных полей. Скрытая тема и дополнительные условия отсекаются в SQL по этапу, началу приёма и времени публикации. Учётные данные не запрашиваются; раскрытые публичные имена берутся только из снимка окончательной публикации.
- `src/db/public-stories.ts` — единый серверный фильтр чтения для списков, метаданных и прямых ссылок; белый список полей с publicAuthorName только после успешной окончательной публикации.
- `src/app/contests/[slug]/stories/[storyId]/page.tsx` — публичное чтение; `src/components/story-text.tsx` и `src/lib/story-content.ts` — безопасные текстовые компоненты и проверка JSON. Не используйте `dangerouslySetInnerHTML`.
- `src/auth/` — server-only: конфигурация, Argon2id, сессии iron-session с хешами в SQLite, атомарные токены, лимиты и почта.
- `src/app/api/account/[action]/route.ts` — только POST, Origin/Fetch-Metadata CSRF, лимит тела, серверная Zod-валидация.
- `src/app/{register,login,registration-status,confirm-email,forgot-password,reset-password,account}/` — интерфейс; кабинет только через `requireVerifiedUser`.
- `src/instrumentation.ts` и `next.config.ts` — проверка конфигурации; next.config отклоняет неверную production-конфигурацию ещё до начала обслуживания запросов. `src/auth/settings.ts` — общая серверная проверка для конфигурации Next и server-only обёртки `config.ts`, не импортировать её в клиент. В production local-почта запрещена, SMTP и HTTPS обязательны.
- `drizzle.config.ts`, `drizzle/` — генерация и версионируемые SQL-миграции со снимками.
- `scripts/migrate.ts`, `scripts/seed.ts`, `scripts/demo-contests.ts` — CLI и вымышленные данные. Не импортируйте seed в приложение.
- `tests/database.test.ts`, `tests/pages.test.ts` — интеграционные проверки только на новых временных базах.

`Participation` связывает автора и конкурс. Рассказ принадлежит участию того же конкурса. Группы имеют тур; `story_rounds` хранит состояние/снятие/результат отдельно по турам. Это сохраняет первый тур при снятии в финале. Бюллетени уникальны по участию и туру; позиции уникальны по рассказу и месту. Составные FK проверяют совпадение конкурса, тура и группы. Связанные исторические данные защищены от каскадного удаления. Разделённые места разрешены.

Текст рассказа — JSON-массив абзацев с текстовыми фрагментами и необязательными bold/italic, не готовый HTML. Для старых данных длина nullable. По текущему запросу новые подачи используют временную версию unicode-codepoints-paragraph-lf2-v1 из src/lib/submission.ts; это не утверждённое конкурсное правило, не меняйте соглашение без явного описания версии и совместимости. Проверки прав, запрета голосования за себя, этапов и полноты бюллетеня обязательны при будущем добавлении операций записи. Не считайте существование строки бюллетеня доказательством действительного голосования.

Правила публикации уточнены в docs/submission_visibility_decisions.md: при приёме на конкурсе видны только свои работы подтверждённого пользователя, private/no-store; сразу после успешного формирования допущенные распределённые работы и ZIP доступны всем, до даты первого тура. src/db/story-publication.ts — единые предикаты. Новая группировка записывает publishedAt атомарно, существующий успешный снимок тоже открывает чтение без перезаписи истории. Старые группы без снимка используют прежнюю проверку publishedAt/старта первого тура. Снятые/неподходящие работы и failed не публикуются. Авторство до окончательной публикации не раскрывается.

Справочный объём ≈ при NULL-длине — отображение Unicode-кодовых точек с двумя переводами строк между абзацами, без заголовка и разметки. Не сохраняйте его как конкурсную длину и не используйте в конкурсных алгоритмах.

Не раскрывайте авторство до конца голосования всего конкурса, включая финал, и тему до публикации при старте. Поля `votingEndedAt` и `publishedAt` — места хранения фактов, не работающий планировщик. Открытые вопросы перечислены в README и документе требований.

## Команды

Node.js 26.13.0 указан в `.nvmrc`. Установка: `nvm install`, `nvm use`, `npm ci`. При первом запуске скопируйте `.env.example` в отсутствующий `.env`; существующий не перезаписывайте. `DATABASE_URL=file:./data/grelqa.db` — путь от корня проекта.

- `npm run db:generate` — сгенерировать SQL после изменения схемы; просмотреть перед применением.
- `npm run db:migrate` — создать файл базы/каталог и применить неприменённые миграции.
- `npm run db:seed` — транзакционно добавить демозаписи; повторный запуск не перезаписывает и не удаляет существующие данные. Конфликты с чужими email/slug приводят к откату. Автосброса нет.
- `npm run dev` — локальная разработка.
- `npm run lint`, `npm run typecheck`, `npm run check` — ESLint, TypeScript, обе проверки.
- `npm run test:db` — новая база в `/tmp`, повторные миграции/seed, ограничения, история, публичные поля.
- `npm run build` — производственная сборка; не требует рабочей базы.
- `npm run test:pages` — после build; новая временная база и временный локальный сервер, проверка HTML/RSC, чтения из базы и отсутствия секретов.
- `npm start` — запуск готовой сборки с мигрированной базой.

Перед сдачей запускайте check, test:db, build, test:pages, test:auth, test:submissions и test:grouping. test:auth требует сборку, использует только временные базу и каталог писем. Не используйте рабочую базу для разрушительных проверок. Тесты сами задают URL и удаляют только собственные временные каталоги. Не коммитьте SQLite, journal/WAL/SHM, .env и секреты. Сохраняйте схему, SQL-миграции, снимки и lock-файл. Не редактируйте применённые миграции; добавляйте новые. Не запускайте db:push/reset вместо миграций.

Полная модель и нерешённые правила описаны в README. Документация Next.js: `node_modules/next/dist/docs/`, если поставляется с выбранной версией; официальная: https://nextjs.org/docs. Drizzle SQLite: https://orm.drizzle.team/docs/get-started/sqlite-new.

## Аутентификация

`auth_sessions`, `auth_tokens`, `auth_rate_limits` добавлены миграцией 0001 без сброса старых данных. Новые пароли — Argon2id; старые seed-хеши scrypt сохраняются. Email: ASCII, trim + lowercase во всех обработчиках, уникальный индекс lower(trim(email)). Не меняйте правила нормализации отдельно для входа и регистрации.

Не храните сырые токены/сессии в SQLite. Используйте стандартные crypto.randomBytes/SHA-256, библиотеки Argon2 и iron-session; не создавайте собственные криптографические алгоритмы. Любая выдача сессии проверяет актуальность хеша пароля в транзакции. Отзыв сессий проверяется по БД на каждом запросе, а сброс пароля, расходование токена и отзыв всех сессий — одна транзакция. Не добавляйте кеш, который задерживает отзыв.

До подтверждения — только состояние регистрации, resend и выход в личной области; публичное чтение доступно как анонимному читателю. Новые операции участия должны вызывать requireVerifiedUser или аналогичную серверную проверку. Не показывайте email/ID вошедшего пользователя в публичной шапке: там только ссылки состояния. Собственный email допустим в закрытом кабинете/статусе регистрации.

Ссылки писем используют fragment #token, чтобы сырые токены не попадали в access-логи. GET не расходует токены; пользователь нажимает кнопку в форме. Не логируйте тела запросов, токены, пароли или исключения ORM/SMTP. Локальные письма только в development, с правами 0600, в .local/mail (Git ignore) или вне проекта. Нельзя сохранять в public. Production обязан проверять SMTP и HTTPS при запуске. Подробные параметры, сроки и лимиты — в README и .env.example.

Команда `npm run test:auth` проверяет полный цикл и серверный доступ на отдельной базе. Реальный SMTP и интерактивное поведение браузерных fragment-форм требуют ручной проверки. Тесты не отправляют письма внешним адресатам.

## Мои работы и редактор

- `src/stories/service.ts` — server-only: запросы владельца, доступность действий, транзакционные сохранение и снятие. Внутри write-транзакции повторно проверяйте активную сессию/email, владельца, stage и start <= now < end; не доверяйте автору, длине, статусу или опубликованности из запроса.
- `src/app/api/stories/[action]/route.ts` — POST save/withdraw, Origin/Fetch-Metadata, 8 МиБ, private/no-store, явное подтверждение снятия. Лимит частоты 120/мин не является конкурсной квотой.
- `src/app/account/layout.tsx` — защита личного раздела. `account/my-stories` — список/просмотр/редактирование только своих работ; `contests/[slug]/submit` — подача. Не выдавайте приватные названия в метаданных до проверки владельца.
- `src/components/story-editor.tsx` — Tiptap, только абзацы, текст, bold/italic и hardBreak. Явное сохранение, предпросмотр через StoryText, предупреждение несохранённых изменений. Никаких внешних изображений, ссылок, HTML или автосохранения.
- `src/lib/editor-content.ts` — преобразование редактора в прежний StoryContent и обратно. `src/lib/submission.ts` — строгий безопасный формат записи и единый счётчик для клиента/сервера. Не дублируйте алгоритм в редакторе или обработчике.
- `src/lib/return-path.ts` — узкий белый список локального возврата к конкурсу после входа. Всегда проверяйте returnTo также на сервере.

Соглашение v1: Unicode-кодовые точки, включая пробелы; между абзацами два LF, hardBreak один LF; CRLF/CR -> LF; без заголовка/разметки и без NFC/NFKC. Новые длины сохраняются с версией, старые не пересчитываются. Технические пределы и открытые вопросы — в README. Это согласованное для шага временное техническое решение, не новое конкурсное правило.

Новые работы только submitted, publishedAt=NULL. Редактировать можно только submitted без публикации и распределения, в период приёма. Старые draft видны владельцу, но сценарии создания/перевода draft не реализуются; admitted/rejected/withdrawn не редактируются до уточнения поведения. Количество работ одного автора по исходным правилам не ограничено: не вводите квоту. UNIQUE участия и write-транзакция обязательны при конкурирующих подачах.

Миграция 0002 добавляет revision=1. Сохранение меняет updatedAt/revision и сохраняет createdAt. Проверяйте revision, чтобы не затирать другую вкладку. Снятие во время приёма — мягкое удаление submitted без групп; в активном туре меняется только story_rounds текущего тура. Не удаляйте тексты и бюллетени, не сдвигайте позиции, не переписывайте первый тур при снятии в финале. Восстановления нет. Не придумывайте отдельные сроки снятия в промежутках: они остаются открытыми, снятие там закрыто.

`npm run db:demo-submissions` создаёт отдельный конкурс «Проба пера» с открытым приёмом на 30 дней; повторный запуск сохраняет все существующие данные и не продлевает даты. Не правьте пользовательские конкурсы ради демонстрации.

`npm run test:submissions` после build проверяет общий формат/Unicode и приватный цикл HTTP на отдельной временной SQLite, границы, сроки, владельца, конкуренцию, снятие и непубликацию. Полный ручной сценарий редактора и предупреждений — в README.

## Первый тур: согласованные уточнения

Прочитайте также `docs/grouping_decisions.md`: это решения пользователя от 31 октября 2026 года, закрывающие часть открытых вопросов первоначальной спецификации. Не считайте прежние блокировки этих пунктов актуальными; остальные предложения не приняты автоматически. Исходный документ требований не переписан.

- `src/contests/grouping-rules.ts`: E=max(C,ceil(N/F)), G=ceil(N/E); сортировка по длине вверх, затем ранней дате/русскому названию/ID для стабильности; последовательные сбалансированные блоки q/q+1, большие блоки первыми. Не заменяйте на round-robin или блоки i//C, нарушающие баланс.
- Назначение: длина вниз, дата вверх, название Intl.Collator(ru, sort, variant, numeric:false), ID вверх при полном совпадении. ID влияет только на техническое формирование/выбор группы, не на призовые места. Новые снимки содержат selectedStoryId.
- `src/contests/grouping.ts`: development + isDemo, write-транзакция, после окончания приёма на moderation без pending submitted. Только admitted без глобального снятия; сопоставимые сохранённые длины одной версии. Никакого автоматического допуска или пересчёта неизвестных длин.
- На этом checkpoint по допущенным проверяются ноль/одна работа/один автор и своевременность темы. enteredAt <= start разрешено. failed, все причины и приватный снимок проверки сохраняются одной транзакцией. Пробельная тема остаётся открытым вопросом и сама по себе не превращается в failed без принятого решения.
- `first_round_formations.snapshot` хранит union успешного и failed-результата, без изменения SQL-схемы. Версии size-blocks-v2 / admitted-viability-v1. Старый unambiguous-single-group-v1 всегда возвращается как есть: не переигрывайте его под новые правила. Повторный/конкурентный вызов возвращает прежний исход, не меняет назначения после снятий. Первичная операция после старта запрещена, старая история без снимка не переписывается.
- `src/contests/grouping-queries.ts` и публичные запросы показывают состояние/разрешённые группы, а кабинет — только собственное назначение. Приватный снимок и авторство не выдаются. Опубликованные пустые группы сохраняют якоря. Формирование сразу публикует допущенные распределённые рассказы; голосование первого тура реализовано отдельно, начало тура требует stage=round-one и наступившего старта.

Команды: `NODE_ENV=development npm run db:demo-balanced-groups`; `NODE_ENV=development npm run contest:close-reception -- demo-first-round-blocks`; `NODE_ENV=development npm run contest:form-groups -- demo-first-round-blocks`. Новый сценарий отдельный, N=10/C=2/F=3 -> E=4, группы 4/3/3; старые примеры и пользовательские конкурсы не меняются. Прежний db:demo-grouping остаётся идемпотентным одногрупповым примером.

`npm run test:grouping` после build проверяет конкретные блоки, увеличение, критерии назначения, конкурентные процессы, rollback обеих ветвей, старые снимки, failed, защиту и HTTP-приватность только на временных SQLite. Полный алгоритм и команды описаны в README. Голосование/финал/модераторский UI/планировщик не добавляйте без отдельного запроса.

## Публичный ZIP-экспорт

- `src/db/public-stories.ts`: `getPublicStoryGroupContents` возвращает единый транзакционный снимок публичного списка с полным содержимым; `getPublicStoryGroups` убирает текст из данных списка. Общий фильтр чтения обязателен для экспорта, списка и прямых страниц.
- `src/exports/markdown.ts`, `filenames.ts`, `archive.ts`: Markdown из проверенного StoryContent, безопасные кириллические имена/коллизии, серверный fflate. Не интерпретируйте HTML; авторство включайте только через publicAuthorName из снимка окончательной публикации. Порядок соответствует сайту. При совпадающих номерах туров согласованы `Первый тур/1`, `Финал/1`, для ungrouped — `Без группы`.
- `src/exports/service.ts`: только публичный вариант, новый снимок доступа перед каждым скачиванием и повторно после получения готового файла. Не выдавайте архивы личных работ через этот endpoint. Ключ учитывает реальное содержимое и распределение, а не только даты. При расширении ролей отдельный вариант ключа и повторная проверка прав обязательны.
- `src/exports/cache.ts`: приватный файловый кэш `.local/exports`/`EXPORT_CACHE_DIRECTORY`, SHA-256, общая межпроцессная блокировка с heartbeat, атомарный rename, очистка. Никаких server-only/next/headers импортов в ядро CLI. managerToken === undefined оставляет CLI development/isDemo; явная строка требует проверенной сессии. HTTP никогда не принимает токен менеджера из payload и не вызывает CLI-ветвь. Права проверяются внутри прежней writeTransaction до возврата существующего снимка.
- `src/management/service.ts`, settings.ts: server-only операции и Zod/календарная проверка МСК; CAS ревизии. Создатель сначала владелец; передача владения только в подготовке. После публикации настройки закрыты. Отдельное назначение координатора owner-only, только незавершённый конкурс; не открывает изменения правил. Ввод темы блокирует перенос начала даже в draft.
- Ядра grouping/close-first-round/prepare-final/finalize используют прежние алгоритмы, получают необязательную серверную сессию для веб-пути, пишут административный журнал в той же транзакции. Audit error откатывает бизнес-операцию. Повторный вызов возвращает snapshot без дубля события. Не добавляйте overwrite или общий setStage.
- `src/stories/withdrawal.ts` — общая низкоуровневая запись снятия текущего тура с refresh освобождений. Автор и модератор проверяют canWithdraw/права/закрытые снимки до неё. Модерация submitted→admitted/rejected только на moderation, до групп, с причиной; снятие active — текущий тур до дедлайна; rejected/withdrawn не восстанавливать, текст не менять. story.status и первый тур не переписывать при снятии финала.
- `src/app/api/manage/[action]/route.ts`: POST strict JSON 64 KiB, Origin/Fetch-Metadata, подтверждения, rate limit, private/no-store. Сессия только cookie. Не логировать ошибки ORM/тела/тему/токен. `managementView` выдаёт только анонимные поля работ и агрегаты существующего coordinatorVotingStatuses; никаких author/participation IDs, чужих ballots/drafts. coordinatorVotingStatuses теперь принимает и владельца, и координатора в своей транзакции. Журнал в БД содержит проверяемые before/after, но DTO event-view.ts проецирует безопасные подписи, без служебных связей и скрытой темы.
- `/manage`, `/manage/new`, `/manage/[slug]` — проверка сервером, generic metadata и noindex. `/enter-theme` — без регистрации; токен из fragment отправляется только POST body; GET не расходует. no-store/no-referrer задаются metadata и HTTP headers. Токен показывается только в ответе выдачи владельцу, не хранится в состоянии страницы после обновления. В базе только SHA-256; повторная выдача отзывает старый. Срок min(7 суток, начало), ввод <= границы; тема/условия вставляются с publishedAt=start, в управлении только факт ввода. Не создавайте фиктивную пустую тему ради токена. Token-recipient audit имеет actorId=NULL, явно отличён от аккаунта владельца.
- RSS/Atom publicUpdatedAt обновляется атомарно для новых публичных административных изменений. Черновики исключены; GUID/дата объявления прежние. ZIP строится из прежнего публичного фильтра и перепроверяет ключ перед ответом: снятые работы не возвращаются из старого кэша.

Команды: npm run db:migrate; NODE_ENV=development npm run db:demo-management — два отдельных повторяемых сценария без обновления старых/user конкурсов. Вход восстановлением management-owner@grelqa.example / management-coordinator@grelqa.example через локальную почту. Первого глобального администратора назначать не нужно по принятому решению; создание доступно подтверждённым аккаунтам. Назначение координатора — владелец, поле в подготовке или отдельная форма после публикации.

Проверки после build: npm run test:management и npm run test:management:browser (CHROMIUM_PATH). Отдельные SQLite/почта/кэш; создание, роли/чужая страница и POST, даты/CAS, токены/отзыв/expiry/гонка, скрытая тема, история модерации, переходы/повтор/конкуренция/rollback, ZIP/ленты, браузерная ссылка/публикация/модерация/телефон. Все прежние check/build/db/pages/auth/submissions/grouping/exports/feeds/voting/closure/final-voting/finalization и обе прежние browser-проверки сохраняются. Не применяйте разрушительные тесты к рабочей базе.

Техническое ограничение новой формы подготовки: резервная дата начала финала обязательна, поскольку количество групп неизвестно до окончания приёма. Это предотвращает неисполняемое многогрупповое расписание после блокировки настроек. Алгоритм первого дедлайна остаётся roundTwoStartAt ?? endsAt; одна группа завершается своим первым итогом без создания финала. Существующие nullable даты и демосценарии не меняются.

Неподанные legacy-черновики рассказов не выдаются координатору/владельцу в списке модерации: их просмотр не нужен для разрешённых действий. История поданных, отклонённых и снятых работ сохраняется.

## Автоматические переходы по расписанию

Текущий запрос добавляет явный standalone worker поверх прежних операций; docs/grelqa_rules_and_spec.md сохраняется как исторический документ v0.10. Не меняйте конкурсные алгоритмы или опубликованные снимки ради расписания. `npm run dev/start/build` не запускают worker. Глобального HTTP endpoint, таймера Next.js и автоматической установки systemd нет.

- `src/scheduling/plan.ts`: только план следующего действия из stage/снимков. Опубликованная preparation — в submissionsStartAt; submissions — в submissionsEndAt; автоматическое form и start-first — не ранее roundOneStartAt. Это сохраняет промежуток модерации; явное ранее разрешённое ручное формирование не меняется. Pending submitted/пустая тема/несопоставимые длины блокируют зависимые действия без автоматического допуска. Дедлайн первого тура roundTwoStartAt ?? endsAt; затем закрытие, при нескольких группах подготовка финала, при единственной — окончательная публикация из первого снимка. Финал закрывается в endsAt. Failed после темы/формирования не требует вымышленного финала; failed закрытого первого тура фиксируется окончательным снимком.
- `src/scheduling/execute.ts`: единый executor для панели и worker. SQLite writeTransaction охватывает выбор действия, авторизацию, прежний сервис и contest_transition_runs. Вложенная транзакция сервиса — SAVEPOINT; ошибка откатывает бизнес-записи, затем внешний commit сохраняет безопасную диагностику. Ошибка самого журнала откатывает весь переход. Между операциями блокировка отпускается. Два worker и панель могут чередоваться, но не применяют одновременно одну операцию и не дублируют успешную запись; решение перечитывается под блокировкой. Lease/TTL/pid-файлов нет: авария освобождает SQLite lock и откатывает незавершённый commit, устаревший исполнитель не получает продолжения. Не заменяйте атомарное решение чтением до write-транзакции.
- `src/scheduling/authority.ts`: nonserializable Symbol для системного исполнителя. Это не аккаунт администратора и не строковый payload; API не принимает authority/clock/time от клиента. Панель передаёт только серверный session token, роль перепроверяется в каждой транзакции, в том числе до noop. Прежний CLI без authority сохраняет development/isDemo; worker имеет отдельный системный путь для опубликованных конкурсов. Admin event системного перехода имеет actorId=NULL и явный actor=scheduler; частные бюллетени, темы и токены не логируются.
- `src/contests/start.ts`: общий проверяемый старт приёма/первого тура, вынесен из панели. Для восстановления после простоя убраны только верхние временные запреты старта первого тура/подготовки финала: разрешено зафиксировать пропущенное состояние, затем сразу закрыть его по исходным датам. Подача и голосование по-прежнему проверяют start <= receivedAt < deadline, независимо от stage worker. Даты не продлевать и голоса не создавать. `refreshRoundOne/TwoExemptions(..., initialize=true)` только при первичном создании назначения/допуска; инициализация нулевого выбора нужна и при поздней подготовке. Обычный refresh после дедлайна остаётся замороженным; санкции/снимки не пересчитываются.
- `src/scheduling/process.ts`: до 10 переходов конкурса и 100 попыток на проход. Следующий запуск продолжает с последнего commit. При общем лимите не посещённые/давно посещённые конкурсы идут раньше, чтобы повторяющаяся ошибка не создавала голодание остальных. Ошибка одного конкурса не блокирует другие. При недоступной БД/журнале отчёт CLI безопасен, но запись ошибки в ту же недоступную БД не гарантируется.
- Миграция 0010 добавляет только contest_transition_runs с FK, outcome/source CHECK и монотонным ID для порядка событий при одинаковом времени. Никаких UPDATE старых конкурсов. Журнал содержит action/source/actor/time/outcome/safe message. Повтор успешной операции — noop без дубля. Невыполненные blocked/error попытки журналируются отдельно, не выдавайте их за успешный переход.
- `/manage/[slug]` показывает lastSuccess, lastError (с пометкой последующего успешного перехода), next/overdue и безопасную историю. `retry-schedule` — POST только подтверждённому владельцу/координатору, с CSRF/лимитом/подтверждением, только его конкурс и наступившие действия. Нет обхода дат. `src/server/clock.ts` — AsyncLocalStorage текущих серверных часов; production использует реальные часы, тесты внедряют фиксированное время без ожидания дедлайнов. Никаких production-переменных или CLI-флагов для подмены часов.
- Все прежние публичные фильтры остаются: тема только после фактического старта и даты, авторство только после успешной finalization. publicUpdatedAt/admin event/итог пишутся атомарно, RSS/Atom сохраняют GUID/pubDate, ZIP сверяет текущий публичный снимок до и после сборки. ZIP не строится внутри перехода; его ошибка не отменяет завершение.

Команды: `npm run schedule:run` (все опубликованные конкурсы), `npm run schedule:run -- --contest slug` (один); exit 0 — всё наступившее выполнено/ничего не наступило, 1 — blocked/error/configuration, 2 — только лимит (повторить). Business failed с успешно сохранённой причиной — успешный переход, не ошибка worker. Отдельная проверочная база: DATABASE_URL=file:./.local/schedule-demo.db npm run db:migrate; NODE_ENV=development DATABASE_URL=file:./.local/schedule-demo.db npm run db:demo-schedule. Seed новый demo-schedule-live, не меняет существующие сроки и не создаёт бюллетени. Не запускайте общий worker на рабочей базе для проверки. Миграции допустимы без сброса после backup; пользовательские конкурсы и опубликованные итоги не менять.

`deploy/systemd/` содержит service/timer/env.example с /srv/grelqa, /opt/node/bin/node, отдельным пользователем и одной SQLite приложения. Это шаблоны: настройку путей/Node/прав/EnvironmentFile делает оператор, не исполняйте install/enable/start без отдельного запроса. Требуется Node из .nvmrc и tsx; worker использует исходники TS, поэтому npm ci без --omit=dev. Запуск примерно раз в минуту, время выполнения/нагрузка/простой могут задерживать публикацию, но не продлевают дедлайны приёма/голоса. Journal/stop/retry описаны в README. Не добавляйте интерактивную nvm-сессию в unit.

Проверки после build: npm run test:schedule, все прежние check/db/pages/auth/submissions/grouping/exports/feeds/voting/closure/final-voting/finalization/management и три browser-набора. Новая временная SQLite, управляемые часы, реальный полный цикл с сервисом бюллетеней, точные границы, модерационный промежуток, late zero-choice и sole-author, простои/лимиты, private data, rollback trigger, два процесса + manual, SIGKILL незавершённой транзакции, in-flight write, кэш/ленты и коды CLI. Миграции на новой базе повторяются. Системные службы не запускаются тестом.
