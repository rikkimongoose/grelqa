# Grelqa

Движок анонимных литературных конкурсов на Next.js App Router, React и TypeScript. Публичные страницы читают локальную SQLite через Drizzle ORM. Литературное оформление, мобильные стили и системные шрифты сохранены.

## Установка и запуск

Node.js **26.13.0** указан в `.nvmrc`. Совместимость проверена: Next.js 16.4.3 требует Node >=20.9; ESLint 10.14.0 — ^20.19, ^22.13 или >=24; TypeScript 5.9.3 — >=14.17; tsx 4.23.15 — >=18. Drizzle ORM 0.45.4 поддерживает `@libsql/client` >=0.10, используется 0.18.0; Drizzle Kit — 0.31.11. Драйвер работает с локальным SQLite, облачный аккаунт не нужен.

В `overrides` адресно обновлён вложенный esbuild у `@esbuild-kit/core-utils` до 0.25.12: это устраняет известную уязвимость зависимости Drizzle Kit. Генерация миграций с ним проверена. Существующий ESLint 10 сохранён; npm предупреждает о диапазонах peer-зависимостей некоторых плагинов Next.js, но установка, линтер и сборка проходят.

```bash
nvm install
nvm use
npm ci
# Только при первом запуске, если своего .env ещё нет:
cp .env.example .env
# В .env задайте SESSION_SECRET (команда генерации ниже), APP_URL и MAIL_MODE.
npm run db:migrate
npm run db:seed
npm run dev
```

Откройте http://localhost:3000. Если nvm отсутствует, установите указанную версию Node другим способом. Существующий `.env` не перезаписывайте: добавьте в него `DATABASE_URL=file:./data/grelqa.db`. Путь относительно корня проекта; разрешены только локальные `file:` URL.

`db:migrate` создаёт каталог и файл базы, применяет только ещё не выполненные миграции. `db:seed` необязателен: без него список конкурсов пуст. Приложение не применяет миграции и не запускает seed автоматически. Сборка не требует существующей базы; для запуска страниц нужна мигрированная база.

## Проверки и производственный режим

```bash
npm run check
npm run test:db
npm run build
npm run test:pages
npm run test:auth
npm run test:submissions
npm run test:grouping
# npm start требует production-настройки HTTPS и SMTP.
npm start
```

- `check` — ESLint и TypeScript; отдельно: `npm run lint`, `npm run typecheck`.
- `test:db` — новая временная база в `/tmp`: повторные миграции и seed, сохранность пользовательских записей, уникальность, внешние ключи, ограничения, история туров и фильтрация секретных данных.
- `test:pages` — требует готовую сборку; создаёт другую временную базу и временный локальный сервер на свободном порту. Проверяет HTML и RSC-ответы главной, конкурсов и рассказов, чтение изменённого в SQLite названия, списки групп, пустое состояние, экранирование HTML, форматирование и отсутствие секретной темы, условий и данных авторства. Проверяет неизвестные ссылки и запрет прямого открытия скрытых работ и работ на закрытых этапах. Затем закрывает сервер и удаляет только собственный временный каталог.
- `build` — производственная сборка; `start` запускает её с настройками из `.env`.

Тесты сами задают `DATABASE_URL`, не используют рабочую базу и не сбрасывают её.

## Модель хранения

Схема: `src/db/schema.ts`; SQL-миграции и снимки: `drizzle/`. Типы выводятся из Drizzle-схемы, дополнительные классы моделей не используются.

| Таблица | Назначение и связи |
| --- | --- |
| `users` | Уникальный email, хеш пароля, дата подтверждения email. Публичное имя пока не определено. |
| `contests` | Организатор → User, slug, описание, ссылка обсуждения, ограничения длины и вместимости, точные даты, этап и причина несостоявшегося конкурса. |
| `contest_themes` | Одна тема и массив дополнительных условий на конкурс; моменты ввода/публикации, необязательные поля одноразового доступа. |
| `participations` | Одно участие User в Contest; назначенная группа первого тура, флаг финалиста и обязанности голосовать по турам. |
| `contest_groups` | Группы с номером, туром и вместимостью; уникальный номер внутри конкурса и тура. |
| `stories` | Название, автор через Participation, структурированный Unicode-текст с абзацами, курсивом и полужирным; даты, статус, длина и версия алгоритма подсчёта. |
| `story_rounds` | Рассказ в группе конкретного тура, снятие с датой/причиной и необязательные итоговые очки/место. Снятие в финале не меняет первый тур. |
| `ballots` | Один бюллетень Participation за тур, группа, даты создания/обновления/отправки. |
| `ballot_entries` | Рассказ и место 1–6; рассказ и место не повторяются в одном бюллетене. Очки не дублируются. |

Все соединения включают `PRAGMA foreign_keys=ON`. Составные внешние ключи не позволяют связывать участие, рассказ, группу и бюллетень из разных конкурсов/туров; позиция бюллетеня ссылается на рассказ в той же группе. Удаление связанных записей ограничено (`RESTRICT`); снятие сохраняет рассказ, бюллетени и позиции. Места в `story_rounds` не уникальны: разделённые места допустимы. Даты хранятся как Unix-миллисекунды, отображаются в МСК. Начало приёма в 15:00 МСК и не более одного старта в день проверяются ограничениями SQLite. Нулевой минимум/максимум означает отсутствие соответствующего ограничения длины.

Окончательный конкурсный алгоритм Unicode-подсчёта пока не утверждён. У прежних записей `length` и `lengthAlgorithm` допускают `NULL`; новые подачи сохраняют длину по временному соглашению с явной версией (см. ниже). Прежние тексты автоматически не пересчитываются. Seed не вводит собственный алгоритм и не выдает короткие тексты-примеры за результат настоящей модерации. Формат структурированного текста и поля публикации — технический выбор этого шага, не новое конкурсное правило.

## Публичные данные и демонстрационные записи

`/` и `/contests/[slug]` читают данные при каждом запросе, без статической копии базы в сборке. `src/db/index.ts` и `src/db/public-contests.ts` защищены `server-only`. Публичные запросы перечисляют разрешённые поля, не читают пользователей, авторство рассказов и бюллетени. Тема и условия присоединяются в SQL только при наступивших начале приёма и `publishedAt`, и вне этапа подготовки. Авторство сейчас вообще не выдаётся; будущая публикация должна учитывать конец голосования всего конкурса, включая финал. Признак `completed` сам по себе не является разрешением раскрытия авторов.

Seed находится в `scripts/seed.ts` и `scripts/demo-contests.ts`: три вымышленных пользователя с неизвестными случайными паролями (хеши scrypt), три конкурса, одна группа, три участия, три рассказа с форматированием (один развёрнутый, два коротких), три бюллетеня и шесть позиций. У будущего конкурса есть настоящая скрытая демотема для проверки непубликации. Даты, ограничения и вручную заданные этапы — параметры примеров.

Seed выполняется транзакцией и только добавляет записи с устойчивыми `demo-*` ID. Он не обновляет существующие записи, не удаляет данные и не сбрасывает базу. Совпадение уникального email/slug с другой записью вызывает ошибку и откат транзакции; это намеренно, чтобы не менять чужие данные. После ручных изменений, конфликтующих с демосвязями, seed также может остановиться вместо перезаписи. Команды сброса базы нет.

## Публичное чтение рассказов

Команды запуска не изменились. В уже заполненной `data/grelqa.db` есть три рассказа: причина их прежнего отсутствия в интерфейсе — отсутствие запросов и компонентов чтения. Повторный seed для такой базы не нужен. Для новой базы выполните `npm run db:migrate` и `npm run db:seed`, как описано выше.

Адреса для проверки:

- `/contests/city-between-lines#stories` — список трёх рассказов в группе первого тура.
- `/contests/city-between-lines/stories/demo-city-story-1` — «Бензин для муниципального апокалипсиса».
- `/contests/city-between-lines/stories/demo-city-story-2` — «Пресс-конференция в лифте без кнопок».
- `/contests/city-between-lines/stories/demo-city-story-3` — «Последний рейс в светлое вчера».
- `/contests/letters-to-november#stories` — пустое состояние.
- `/contests/city-between-lines/stories/unknown` — страница «не найдено».

`src/db/public-stories.ts` защищён server-only. Согласованное уточнение: во время приёма страница конкурса показывает вошедшему автору с подтверждённым email только его работы (приватные ссылки); остальным — пояснение. Чужие рассказы не попадают ни в HTML/RSC, ни в архивы. Приватный список не кешируется публично.

Успешное формирование групп сразу открывает допущенные распределённые рассказы и ZIP, даже на moderation и до даты первого тура. Новая операция записывает publishedAt групп/рассказов атомарно со снимком; для существующих успешных снимков действует то же правило чтения без перезаписи истории. Группы без успешного снимка продолжают использовать прежние publishedAt/этап/дату первого тура — это сохраняет существующие примеры и не публикует вручную созданные скрытые группы. Общие предикаты находятся в src/db/story-publication.ts и применяются к списку, прямому чтению, метаданным и ZIP. Подготовка/приём/failed, неподходящие статусы и снятые работы остаются непубличными. Авторство не запрашивается и не раскрывается.

Подача и редактирование закрыты после завершения приёма или существования групп/снимка, даже если этап ошибочно возвращён в submissions. Даты и права перепроверяются в транзакции. Формирование не запускает голосование автоматически; бюллетень первого тура доступен с его началом. Уточнение записано в [решениях о видимости](docs/submission_visibility_decisions.md).

Список группирует рассказы только по опубликованным группам. Для финалиста используется последняя опубликованная группа доступного тура, остальные работы остаются в группах первого тура; дубликатов рассказов нет. Если опубликованной группы нет, работа показана отдельно, без раскрытия неопубликованного распределения.

`src/lib/story-content.ts` проверяет структуру текста, `src/components/story-text.tsx` выводит только абзацы, текст, `<em>` и `<strong>`. Чужие атрибуты не передаются; `dangerouslySetInnerHTML` не используется. HTML/скрипты в тексте экранируются React. Ширина чтения ограничена, длинные слова переносятся, оформление адаптировано для телефона.

Если сохранённая конкурсная длина отсутствует (`NULL`), интерфейс показывает справочное `≈ N знаков с пробелами`: число Unicode-кодовых точек текстовых фрагментов, между абзацами — два перевода строки; заголовок и разметка не учитываются. Этот объём не записывается в базу, не используется для допуска, групп или результатов и не утверждает пока не согласованный конкурсный алгоритм подсчёта.

## Аутентификация

Добавлены `/register`, `/login`, `/registration-status`, `/confirm-email`, `/forgot-password`, `/reset-password` и `/account`. Состояние входа и выход доступны в шапке. Кабинет проверяет сессию и подтверждение email на сервере. Неподтверждённая сессия допускает только состояние регистрации, повторную отправку и выход; публичное чтение остаётся доступно всем, как и без регистрации. Подача и редактирование доступны в разделе «Мои работы»; голосование пока не реализовано.

Новые зависимости: iron-session 9.0.1 (Node >=22.13), @node-rs/argon2 2.2.2 (Node >=10), Nodemailer 10.3.1 (Node >=20), Zod 4.6.7. Они проверены на Node 26.13.0. Пароли новых пользователей хешируются Argon2id (19 MiB, 2 прохода, 1 поток), старые seed-хеши scrypt сохранены. Пароль — от 12 до 128 символов, без обрезания пробелов. Email обрезается по краям и приводится к нижнему регистру и при регистрации, и при входе/восстановлении; принимается ASCII-email, без специальных правил Gmail/удаления точек/плюсов. Новый уникальный индекс `lower(trim(email))` защищает от гонок. Существующие email не переписываются. Если в старой базе уже есть конфликтующие варианты email, миграция остановится: сначала нужно вручную разрешить конфликт, данные не удаляются.

Миграция `0001_flippant_nemesis.sql` только добавляет индекс и три таблицы: `auth_sessions`, `auth_tokens`, `auth_rate_limits`. Старые миграции, конкурсы и тексты не изменяются. `db:seed` не создаёт известных паролей для демопользователей; зарегистрируйте отдельную учётную запись.

### Локальная проверка писем

1. Выполните `nvm use`, `npm ci`, `npm run db:migrate`. В существующий `.env` добавьте недостающие поля из `.env.example`, не перезаписывая DATABASE_URL.
2. Создайте SESSION_SECRET командой ниже и сохраните результат в `.env`. Не публикуйте секрет. Укажите `APP_URL=http://localhost:3000`, `MAIL_MODE=local`, `MAIL_DIRECTORY=.local/mail`.
3. Запустите `npm run dev` и откройте `/register`. Введите email и дважды пароль. До подтверждения `/account` переводит на `/registration-status`.
4. В терминале появится только путь к JSON-письму в `.local/mail`. Откройте файл в редакторе и скопируйте полную ссылку, включая `#token=…`, в адресную строку браузера. Нажмите «Подтвердить email». Простое открытие ссылки ничего не меняет — почтовые сканеры не расходуют её.
5. Перейдите в кабинет; обновите страницу. Выполните выход и снова войдите. Для проверки повторной отправки используйте неподтверждённую учётную запись и кнопку на странице состояния регистрации.
6. На `/forgot-password` запросите письмо. Откройте новую ссылку из файла, введите новый пароль дважды. Старые сессии на всех устройствах должны потерять доступ; старый пароль больше не подходит. Повторная ссылка сообщает об использовании; просроченная — об истечении срока. Подтверждение действует 24 часа, сброс — 30 минут.

```bash
node -e "console.log(require('node:crypto').randomBytes(48).toString('base64url'))"
```

Локальные письма содержат секретные ссылки, сохраняются с правами 0600, каталог создаётся с 0700. Внутри проекта разрешён только игнорируемый `.local/`, либо можно указать отдельный каталог вне проекта. Письма никогда не размещаются в `public`. Папка `.local/` исключена из Git. В обычных логах нет паролей и токенов; fragment ссылки не уходит в HTTP/access-логи. Не переносите токен в query string. Формы требуют JavaScript.

### SMTP и production

В production задайте `APP_URL=https://ваш-домен`, случайный `SESSION_SECRET`, `MAIL_MODE=smtp`, `MAIL_FROM`, `SMTP_HOST`, `SMTP_PORT`, `SMTP_SECURE` и при необходимости пару `SMTP_USER`/`SMTP_PASSWORD`. `SMTP_SECURE=true` обычно используется с портом 465; для 587 — false и STARTTLS. В production STARTTLS обязателен, если не включён implicit TLS; проверка сертификата не отключается. Ссылки строятся только от APP_URL, а не от Host/X-Forwarded-Host запроса. SMTP-секреты не попадают в браузер и логи.

Локальная почта допускается **только** в development (`npm run dev`). `npm start` с MAIL_MODE=local либо неполной почтовой конфигурацией завершится явной ошибкой конфигурации. Перед `npm start` настройте SMTP и HTTPS. Сборка не отправляет письма и не требует рабочей базы. Для проверки реальной доставки, TLS и попадания в почтовый ящик необходим настроенный SMTP-сервис — эти действия выполняются вручную.

### Сессии и защита

В cookie находится только защищённый iron-session случайный идентификатор; SQLite хранит его SHA-256-хеш. Срок сессии — 30 дней без автоматического продления. Cookie — HttpOnly, SameSite=Lax, Path=/; в production Secure и префикс `__Host-`, без Domain. Каждый запрос кабинета проверяет существование и срок сессии в базе; браузерный кеш cookie не заменяет отзыв на сервере. Новый вход меняет идентификатор текущей сессии, выход удаляет её, сброс пароля удаляет все сессии пользователя.

Токены из 32 случайных байт хранятся только как SHA-256 с разделением назначения (`verify`/`reset`). Расходование по `usedAt`/`expiresAt`, изменение пользователя и отзыв сессий выполняются одной транзакцией; использованные записи остаются для понятного сообщения о повторе. Сброс также отзывает остальные ссылки сброса. Пароль никогда не извлекается и не отправляется.

Все изменения — POST `/api/account/[action]`, с обязательной точной проверкой Origin против APP_URL и запретом Sec-Fetch-Site=cross-site. CORS не разрешён. GET не меняет состояние. Формы ограничены 8 KiB, валидируются Zod на сервере, ошибки не возвращают SQL/SMTP-исключения. Регистрация проверяет повтор пароля и уникальность email; восстановление возвращает одинаковое сообщение при неизвестном email, лимите для адреса и ошибке доставки. Поиск адреса и отправка восстановления выполняются через Next.js after после ответа, чтобы длительность SMTP не выдавала существование аккаунта. Это не долговечная очередь: если процесс оборвётся до отправки, запросите письмо повторно.

Счётчики SQLite сохраняются при перезапуске: вход — 5 попыток на адрес за 15 минут; регистрация — 3 на адрес в час; письма — 3 на пользователя и назначение в час; запрос восстановления — 3 на адрес в час. Дополнительно общий лимит: 100 входов или 30 запросов каждого другого действия за 15 минут (кроме выхода). Это сознательные начальные настройки для одного локального сервера; в большом развёртывании потребуется настроить лимиты под нагрузку. Подставляемому X-Forwarded-For приложение не доверяет. Никакой глобальный лимит не блокирует выход.

`npm run test:auth` после build автоматически проверяет HTTP-регистрацию, нормализацию/уникальность, повтор пароля, ограниченную сессию, production-атрибуты cookie, CSRF, конкурентное расходование, истечение и повтор токенов, вход/выход, сохранение и истечение сессий, отзыв после сброса, отказ старому паролю, доступ к кабинету и лимиты. Проверяет сохранение писем в development и запрет local/неполного SMTP в production. Используются только отдельная временная SQLite и каталог писем. Production HTTP-сервер теста обращается к закрытому локальному SMTP-порту; успешную файловую доставку проверяет сервис в development. Реальная доставка SMTP и клики в браузере проверяются вручную по шагам выше.

Документация: [iron-session](https://github.com/vvo/iron-session), [Nodemailer SMTP](https://nodemailer.com/smtp/).

## Мои работы, подача и редактирование

Миграция `0002_fantastic_zombie.sql` добавляет только `stories.revision DEFAULT 1`: это версия для защиты от перезаписи двумя вкладками. Старые тексты, даты, статусы и аутентификация не меняются.

```bash
nvm use
npm ci
npm run db:migrate
# Отдельный пример для ручной проверки, без изменения существующих конкурсов:
npm run db:demo-submissions
npm run dev
```

`db:demo-submissions` транзакционно добавляет вымышленные учётную запись организатора и конкурс **«Проба пера»** (`/contests/demo-open-submissions`) с минимумом 10, максимумом 20 000 и приёмом на 30 дней с момента создания примера. Начало — свободный прошедший день в 15:00 МСК, без нарушения уникальности дня старта. Повторный запуск ничего не перезаписывает и не продлевает приём; это не автоматическая смена этапов. Пароль организатора случаен и неизвестен, используйте свою зарегистрированную учётную запись для подачи. Обычный `db:seed` остаётся независимым и не меняет эти данные.

Адреса:

- `/account/my-stories` — только свои работы, конкурс, объём, статус, приватный просмотр и доступные действия; список открытых конкурсов для добавления.
- `/contests/[slug]/submit` — подача в конкретный конкурс.
- `/account/my-stories/[id]` — приватное чтение своего текста, даты и снятие.
- `/account/my-stories/[id]/edit` — редактирование при разрешённом статусе и сроках.

Раздел доступен только вошедшему пользователю с подтверждённым email, ссылка есть в кабинете и навигации. На странице открытого конкурса анонимный пользователь получает ссылку входа, неподтверждённый — подтверждения email, подтверждённый — подачи. `returnTo` проверяется на сервере по узкому белому списку локальных `/contests/<ASCII-slug>`; внешние, protocol-relative, кодированные разделители и управляющие символы не принимаются. Выбранный конкурс сохраняется и при регистрации/подтверждении в том же браузере.

### Сохранение и статусы

Новая работа сразу получает `submitted`, никогда не `draft` или `admitted`. Отдельных черновиков и автосохранения нет. Существующий модельный `draft` оставлен для совместимости, доступен владельцу для просмотра и не имеет переходов через этот интерфейс: сценарий его использования ещё не определён. Редактировать можно только `submitted`, без публикации и распределения по турам, во время приёма. Редактирование `admitted`/`rejected` и повторная модерация пока не согласованы и закрыты.

Каждое сохранение повторно проверяет в write-транзакции актуальную сессию и email, владельца, конкурс, статус, версию и точное время: `stage=submissions` и `start <= now < end`. Форма, открытая до дедлайна, не даёт права сохранить после него. Сервер сам вычисляет объём; присланные длина, автор, статус и время публикации не принимаются. Если участия ещё нет, `Participation` и рассказ создаются одной транзакцией; UNIQUE(user, contest) предотвращает дубликат участия при конкурирующих запросах. Согласно исходным правилам количество работ автора **не ограничено**, поэтому конкурсный лимит и фиктивное поле квоты не вводятся. Ограничение частоты 120 запросов записи в минуту на пользователя — защита обработчика, а не число допустимых работ.

Редактирование сохраняет `createdAt` как исходную дату подачи; меняет `updatedAt` и увеличивает `revision`. Старая версия получает 409; текст в редакторе остаётся, его можно скопировать перед обновлением страницы. Создание/изменение никогда не выставляет `publishedAt` и не допускает работу: применяются прежние правила публичного чтения. Все приватные страницы динамические, запросы SQLite ограничены владельцем, ответы API имеют `private, no-store`; чужой ID не раскрывает ни текст, ни заголовок.

### Временное соглашение о длине и формате

ТЗ оставляет открытыми единицу Unicode, заголовок, переводы строк, разметку и нормализацию. На этом шаге по запросу пользователя принято **техническое временное соглашение**, не утверждённое конкурсное правило:

- Одна кодовая точка Unicode — один знак; это не число байт, UTF-16 единиц или графем. Обычный emoji может быть одним знаком, `e` + combining accent — двумя, последовательности emoji с ZWJ — несколькими.
- Считаются текст, пробелы и переводы строк. Между абзацами — два LF, Shift+Enter — один LF. CRLF/CR заменяются LF; пустые абзацы сохраняются. Заголовок и разметка не считаются; NFC/NFKC не применяется.
- `src/lib/submission.ts` содержит одну реализацию для браузера, сервера и справочного объёма старых работ. В базу новых подач сохраняется `lengthAlgorithm=unicode-codepoints-paragraph-lf2-v1`. Нулевые минимум/максимум конкурса не ограничивают соответствующую границу.
- Техническая защита ресурса: до 1 000 000 кодовых точек, 4000 абзацев, 16 000 фрагментов и 8 МиБ на запрос, название до 200 кодовых точек. Это новые явно обозначенные технические пределы прототипа, а не прежнее правило 100 000 байт.

Tiptap 3.32.2 совместим с React 19; разрешены только абзацы, текст, курсив, полужирное и простой перевод строки. Ссылки, изображения, списки, заголовки и прочая вёрстка отключены. JSON редактора переводится в прежний `StoryContent`; сервер строго проверяет типы и белый список полей. Произвольный HTML не хранится как исполняемая разметка, буквальный текст `<script>…` безопасно экранируется React и считается обычным текстом. Предпросмотр использует тот же компонент `StoryText`, что публичное и приватное чтение.

Сохранение явное, с сообщением результата. Несохранённые изменения вызывают предупреждение при закрытии/обновлении, переходе по ссылке и браузерной кнопке «Назад»; на мобильных браузер может ограничивать системный beforeunload. Не используйте закрытие вкладки как замену сохранению. Состояние текста хранится только в памяти страницы.

### Снятие и открытые вопросы

Во время приёма автор может убрать свою `submitted` без распределения: вместо физического удаления ставится `withdrawn`, сохраняются текст, даты и причина. В явно активном первом/втором туре можно снять допущенную работу с активной записью `story_rounds` текущего тура, после начала тура и до общего `endsAt`. В туре меняется только эта запись; финал не переписывает первый тур. Все бюллетени и их позиции остаются. Баллы снятой работы должны теряться без сдвига остальных позиций при будущем подсчёте — подсчёт и голосование сейчас не добавлены. Действие требует подтверждения и актуальной версии. Обратного действия нет.

Точные границы снятия в промежутках, отдельное окончание первого тура и возможность восстановления не определены. Дополнительные дедлайны не вводятся: доступ определяется явно текущим этапом и известными датами; условную дату финала не выдаём за универсальный конец первого тура. В подготовке, модерации, завершённом и несостоявшемся конкурсе снятие закрыто до уточнения. Открыты также редактирование допущенных/отклонённых работ, поведение старых draft, окончательный Unicode-подсчёт и окончательные правила снятия. При сохранении подачи публикации нет; успешное формирование групп открывает чтение и ZIP.

### Проверка этого этапа

`npm run test:submissions` после build создаёт отдельную временную SQLite и HTTP-сервер. Проверяет Unicode и преобразование формата, серверный подсчёт, подачу/редактирование, даты/версии, конфликты двух вкладок, параллельные неограниченные подачи с одним Participation, минимум/максимум и нулевые границы, закрытие приёма после открытия формы, чужие ID (просмотр/редактирование/API), закрытые статусы, CSRF, подтверждение email, приватный кеш, отсутствие ранней публикации/авторства, снятие без удаления и сохранение первого тура/бюллетеней при снятии в финале. Тесты никогда не используют рабочую базу. `test:db` дополнительно проверяет обновление старой схемы с сохранением прежних столбцов.

Порядок ручной проверки:

1. Зарегистрируйтесь, подтвердите email и откройте «Мои работы»: сначала пустое состояние. Выйдите, откройте `/contests/demo-open-submissions`, выберите вход; после него должен открыться тот же конкурс.
2. Нажмите «Подать рассказ», введите название и не менее 10 знаков. Создайте несколько абзацев, выделите слова курсивом и полужирным, попробуйте Shift+Enter и emoji. Сверьте счётчик с предпросмотром, переключите мобильную ширину.
3. Измените текст и попробуйте ссылку/Назад/обновление: должно появиться предупреждение. Откажитесь от ухода, затем сохраните и проверьте успешное сообщение.
4. Откройте приватный просмотр и «Мои работы». Работа имеет статус «Подана», публичный список конкурса пока её не показывает. В другом аккаунте прямые приватные ссылки должны быть недоступны.
5. Откройте редактирование в двух вкладках. Сохраните в первой, затем во второй: вторая получит конфликт, её текст не пропадёт. Дата подачи сохраняется, дата изменения обновляется.
6. В приватном просмотре прочитайте последствия, подтвердите и снимите работу. Она остаётся в списке и доступна вам для чтения, но редактировать или восстановить её нельзя.

Операции мышью/клавиатурой Tiptap, мобильное оформление и системные диалоги предупреждения требуют этой ручной проверки; автоматические тесты проверяют формат, общий счётчик и серверный цикл через HTTP.

## Закрытие приёма и формирование первого тура

Уточнения пользователя от 31 октября 2026 года записаны в [docs/grouping_decisions.md](docs/grouping_decisions.md). Они дополняют открытые пункты исходной спецификации; остальные предложения не утверждены автоматически. Прежние распределения не пересоздаются.

### Алгоритм size-blocks-v2

Операция берёт только `admitted` без глобального снятия. При N работах, исходной вместимости C и вместимости финала F вычисляются E = max(C, ceil(N / F)) и G = ceil(N / E). Исходная настройка C не переписывается: эффективная E сохраняется в группах и снимке.

Рассказы сортируются от коротких к длинным. При одинаковой длине для стабильности используются более ранняя дата, название по возрастанию и ID. Названия сравниваются стандартным Intl.Collator с русской локалью, variant и без числовой сортировки. Последовательность делится на **сбалансированные блоки**: q = floor(N / G), первые N mod G групп получают q+1 работу, остальные q. Например, N=10, C=2, F=3: E=4, G=3, размеры **4/3/3**. Это не циклическая раздача и не несбалансированные блоки по исходной вместимости.

Для каждого автора выбирается наибольшая длина, затем самая ранняя точная дата, название от А до Я и стабильный ID при полном совпадении. ID используется только технически для выбора группы и не определяет призовые места. В Participation сохраняется группа; в приватном снимке — также ID выбранного рассказа. Все свои рассказы запрещены для голосования; реального приёма бюллетеней пока нет, будущий серверный обработчик обязан повторять этот запрет.

Все длины должны быть заполнены, неотрицательны и иметь одну версию подсчёта. Неполные/несопоставимые старые данные возвращают blocked с пояснением, а не скрытый пересчёт. Временное Unicode-соглашение предыдущего этапа не изменено и не становится окончательным конкурсным правилом.

### Атомарность и несостоявшийся конкурс

Формирование выполняется одной write-транзакцией libSQL, только после `submissionsEndAt`, на этапе moderation и при отсутствии pending submitted. Явный запуск после завершения проверки — согласованный момент проверки жизнеспособности по допущенным работам. Ноль допущенных, одна работа, все работы одного автора, отсутствующая или поздно введённая тема дают **failed**. Равенство enteredAt и старта теперь допустимо. Причины сохраняются все, без удаления конкурса/текстов/истории. Если результат зависит только от того, считается ли пробельная тема темой, остаётся blocked: этот вопрос ещё не решён.

Группы, story_rounds, назначения, публикация допущенных работ и приватный неизменяемый снимок сохраняются атомарно. Для failed в той же транзакции сохраняются состояние, причины и снимок проверки. `first_round_formations` теперь хранит оба вида исхода в существующем JSON-поле — новая SQL-миграция для этого изменения не нужна. Миграция 0003 по-прежнему нужна для первоначального создания таблицы.

Новые версии: `size-blocks-v2` и `admitted-viability-v1`. Старые `unambiguous-single-group-v1` читаются без изменения данных и назначений. Повторный и конкурентный запуск возвращают **ровно прежний результат**, включая failed и случаи последующего снятия. Уже начатый тур без сохранённого снимка не пересоздаётся; старые seed-группы и бюллетени не переинтерпретируются. Сброса или флага перераспределения нет.

### Интерфейс и публикация

На странице конкурса есть состояния «Группы ещё не сформированы», «Группы сформированы» и «Конкурс не состоялся» с безопасными причинами. Это согласованное уточнение заменяет прежнее ожидание даты тура. Новое формирование сохраняет publishedAt атомарно; старый успешный снимок также открывает чтение без изменения истории. Голосование и смена этапа на round-one автоматически не запускаются. Авторство и приватный JSON-снимок не передаются публичным страницам.

Проверяются конкретные блоки 4/3/3, минимальное увеличение на множестве размеров, максимум длины/ранняя дата/русское название/ID, полное совпадение в разных группах, один рассказ ровно в одной группе, исключение остальных статусов, назначения при нескольких работах, сохранение после реального HTTP-снятия, три конкурентных процесса, повторный запуск, совместимость старого снимка, атомарный откат формирования и failed, все причины failed, допустимое равенство времени темы, незавершённая модерация, неполные длины, запреты после старта и защита development/demo/date. Открыты: пустая/пробельная тема, запуск голосования и дальнейшие моменты повторной проверки несостоявшегося конкурса. Бюллетени, баллы, финал и призовые критерии не изменены.

## Скачивание рассказов в ZIP

На странице конкурса доступны «Скачать конкурс в ZIP» и «Скачать группу в ZIP», когда есть опубликованные рассказы. Регистрация не нужна. Серверный GET `/contests/[slug]/download` экспортирует конкурс, `?group=[ключ группы]` — выбранную группу (в том числе `ungrouped`). Неизвестный конкурс, скрытая/пустая группа или отсутствие доступных рассказов дают 404 с пояснением, ошибка подготовки — 503.

Архив группы содержит `.md` в корне; архив конкурса — папки с отображаемыми номерами групп без внешней папки. Если номера разных туров совпадают, используются `Первый тур/1/` и `Финал/1/`; работы без опубликованной группы помещаются в `Без группы/`. Это уточнение согласовано при реализации экспорта. Порядок совпадает со списком сайта; финалист, как и на сайте, выводится один раз в последней доступной группе.

Файлы UTF-8 содержат заголовок H1, абзацы, полужирное и курсивное выделение, включая их сочетание; смысловые переносы представлены Markdown hard break. Служебные символы экранируются, HTML в тексте остаётся текстом. Имена сохраняют кириллицу, очищаются от разделителей/управляющих символов и запрещённых Windows-имён, ограничены 180 UTF-8 байтами без расширения. Коллизии без учёта регистра разрешаются постфиксами с учётом настоящих названий с постфиксами.

Экспорт использует единый фильтр публичного чтения и никогда не включает авторство, личные работы владельца или скрытые версии. Сейчас опубликованный текст нельзя редактировать через интерфейс; отдельного хранилища неопубликованных правок к опубликованному тексту нет. Если оно появится, экспорт должен продолжить читать только опубликованную версию. Все посетители получают один публичный вариант, независимо от cookie. Привилегированных архивов нет.

ZIP создаётся серверной библиотекой [fflate](https://github.com/101arrowz/fflate) 0.8.3 (Node.js/TypeScript). Новый снимок SQLite для каждого запроса фиксирует состав, порядок и полный текст. SHA-256 ключ включает версию формата, публичный вариант доступа, конкурс/группу, заголовки, распределение и экспортируемое содержимое; `updatedAt` не используется как единственное основание. После сборки/чтения кэша доступ и ключ проверяются повторно. При изменении данных выполняется повторная попытка, при непрерывных изменениях — 503. Ответы имеют `Cache-Control: private, no-store`, чтобы браузер/CDN не обходил серверную проверку доступа.

Кэш хранится в `EXPORT_CACHE_DIRECTORY` (по умолчанию `.local/exports`, уже исключено через `.local/` из Git), вне `public`; каталог должен быть доступен серверу на запись и сохраняться между перезапусками. Файлы имеют права 0600, создаваемый каталог — 0700. Не публикуйте каталог через веб-сервер. Одновременные запросы используют одну сборку, включая отдельные процессы с общим каталогом: файловая блокировка с heartbeat, временный файл и атомарное переименование. Падение сборки не публикует частичный ZIP.

Очистка выполняется при запросах не чаще раза в час на процесс и вручную:

```bash
npm run exports:clean
```

Удаляются ZIP без обращений более семи дней и брошенные блокировки/временные файлы старше десяти минут. Используемые архивы продлевают срок хранения. Это файловый кэш одного сервера/общего локального тома; Redis не требуется. Команда удаляет только файлы с именами формата данного кэша, не базу и не письма.

Проверка: после сборки `npm run test:exports` проверяет Markdown, пути/коллизии, ZIP, одновременную сборку между процессами, повторное использование, ошибки/очистку и HTTP на временной SQLite. Для ручной проверки запустите `npm run dev`, откройте `/contests/city-between-lines`, скачайте конкурс и группу; распакуйте архивы, сравните одноимённые файлы и просмотрите `.md` в Markdown-просмотрщике. Повторное скачивание использует тот же файл кэша. На конкурсе без опубликованных работ вместо ссылок показано пояснение. Проверьте кириллическое имя скачивания в используемом браузере и распаковку на вашей ОС. Демо с успешным снимком формирования сразу выдаёт ZIP допущенных распределённых работ, даже до даты первого тура.

## RSS 2.0 и Atom 1.0

Публичные ленты доступны без входа: `/rss.xml` (`application/rss+xml; charset=utf-8`) и `/atom.xml` (`application/atom+xml; charset=utf-8`). Ссылки находятся в футере, `rel="alternate"` в HTML head позволяет ридерам обнаружить оба формата. Запуск и другие настройки приложения не изменились.

В `.env` задайте `SITE_URL=http://localhost:3000` для локальной проверки или `SITE_URL=https://ваш-домен` при развёртывании. Это HTTP(S) origin без пути, query, fragment и учётных данных, независимый от `APP_URL` для писем. В development при отсутствии SITE_URL используется localhost:3000; для другого порта укажите его явно. В production SITE_URL обязателен только для лент: ошибка настройки/базы возвращает 503 с пояснением и не блокирует остальные страницы. Адреса никогда не берутся из Host запроса.

`src/feeds/data.ts` — единый server-only сервис, читающий существующие `contests` и `contest_themes`. Включаются последние десять тем, видимых по текущей политике страницы конкурса: этап не preparation, начало приёма и publishedAt темы уже наступили. Отсутствующая тема, NULL/future publishedAt и будущий старт исключаются. Конкурсы со своевременно опубликованной темой остаются в ленте после завершения или исхода failed. Уже существующие демозаписи подчиняются тому же фильтру; функция ничего не создаёт и не изменяет.

Дата объявления — max(начала приёма, publishedAt темы), поскольку именно после обеих границ тема становится публичной. Сортировка по ней убывает, при равенстве используется стабильный первичный ID по убыванию. Запись содержит название, абсолютную ссылку, тему, дату объявления и окончание приёма (ISO 8601 в описании). Постоянный идентификатор `urn:grelqa:contest:<SHA-256 первичного ID>` одинаков в RSS/Atom и сохраняется при смене slug/названия/домена. Atom author — название сервиса «Рваная Грелка», а не организатор или автор рассказа. Учётные данные и рассказы не запрашиваются.

В текущей модели нет времени последнего изменения публичных данных конкурса. Поэтому entry.updated использует дату объявления, feed.updated/lastBuildDate — максимальную дату объявления включённых записей. Это ограничение: правки названия, темы или расписания читаются заново, но достоверно датировать их нельзя без отдельного поля/истории изменений. Схема намеренно не изменена. В пустом RSS lastBuildDate опущен; обязательный Atom updated равен постоянной технической отметке 1970-01-01T00:00:00Z, не дате несуществующего объявления. Текущее время не подставляется в даты выдачи. HTTP no-store обеспечивает получение свежего набора без зависимости от сессии.

Сериализаторы `src/feeds/rss.ts` и `atom.ts` изолированы, внешняя библиотека генерации не требуется. XML 1.0 экранируется с удалением недопустимых управляющих символов; Atom summary имеет type=text, RSS description экранирует также текстовый HTML-слой. Нормативные форматы: [RSS 2.0](https://www.rssboard.org/rss-specification) и [Atom RFC 4287](https://www.rfc-editor.org/rfc/rfc4287). Схема, миграции, авторизация, редактор и существующие правила публикации не менялись.

Проверка после сборки: `npm run test:feeds`. Только в отдельной временной SQLite проверяются оба HTTP endpoints без cookie, пустая база, XML/namespace (dev-зависимость saxes), лимит и сортировка, черновики/скрытые темы, экранирование, даты, URL, постоянные ID и ссылки обнаружения. Для ручной проверки запустите `npm run dev` и откройте http://localhost:3000/rss.xml и http://localhost:3000/atom.xml. Браузер может показать исходный XML либо предложить загрузку; обе ссылки можно добавить в RSS/Atom-ридер. При отсутствии объявленных конкурсов ленты остаются корректными и пустыми; дополнительные демоданные не нужны.

## Мой бюллетень первого тура

Участник с подтверждённым email получает ссылку «Мой бюллетень» в кабинете и у назначенной группы: `/contests/[slug]/ballot`. Выбор доступен только на stage=round-one с наступившим roundOneStartAt; публикация рассказов после группировки сама по себе голосование не начинает. Дедлайн по согласованному решению — начало финала (roundTwoStartAt), а без финала — endsAt. Интерфейс показывает дату/время в МСК (UTC+3).

Выбираются только доступные чужие работы назначенной группы. Если их не меньше шести — нужны ровно шесть; если одна–пять — все; при нуле фиксируется освобождение в Participation без пустого отправленного бюллетеня. Снятие своего рассказа не меняет назначение. После снятия выбранной работы отправленный бюллетень остаётся засчитанным, снятая позиция видна владельцу, другие места не меняются; новая отправка необязательна. Баллы/результаты на этом этапе не считаются.

«Сохранить черновик» допускает неполный выбор и не выполняет обязанность голосования. «Отправить бюллетень» проверяет полный актуальный набор и последовательно назначает места с первого. Рабочее соглашение, реализованное по запросу пользователя, но не отдельное окончательно утверждённое конкурсное правило: действующая отправленная версия сохраняется, пока не отправлена новая полная версия; черновик хранится отдельно. Есть кнопки «Выше», «Ниже», «Убрать», дополнительное перетаскивание, работа с клавиатуры и мобильный экран. Предупреждение защищает несохранённый выбор при уходе. Владелец видит время последней успешной отправки.

«Добавить в мой бюллетень» на странице подходящего рассказа сохраняет только черновик. Если его нет, берётся копия отправленной версии. Повторное добавление не дублирует позицию; при заполненных шести местах нужно открыть бюллетень и изменить выбор. Снятые позиции старого черновика нужно убрать перед новой отправкой.

Серверные POST `/api/ballots/draft`, `/submit`, `/add` проверяют сессию/email, назначение/право/этап, время поступления в доверенный обработчик, актуальность работ, автора, количество, уникальность и ревизию. В момент дедлайна новый запрос уже отклоняется. receivedAt из браузера не принимается; получение тела и ожидание блокировки не подменяют серверную отметку. Все связанные изменения выполняются в write-транзакции. Будущий финализатор обязан использовать такой же транзакционный порядок, ожидая текущую запись и перепроверяя этап; сам финализатор ещё не добавлен. CAS ревизии защищает вкладки, requestId+хеш payload — повтор запросов; повтор уже принятого запроса возвращает квитанцию, не создавая новый голос. При отказе текущий выбор остаётся в интерфейсе.

Миграция `0004_majestic_war_machine.sql` добавляет только поля освобождения и таблицы `ballot_drafts`/`ballot_requests`, без сброса и пересоздания конкурсов. Действующая версия использует прежние `ballots` и `ballot_entries`; черновик — отдельный упорядоченный JSON-массив ID с ревизией. Удаление позиций при успешной замене ballot происходит только внутри одной транзакции. JSON черновика проверяется сервером; связанные итоговые позиции защищены прежними FK/UNIQUE. Публичных endpoint результатов нет. coordinatorVotingStatuses — защищённое серверное представление статусов только для организатора, без содержимого и сумм; полноценной панели пока нет. После закрытия обе личные версии доступны для чтения, чужие голоса автоматически не публикуются.

## Закрытие первого тура и итоги

Правила согласованы в ТЗ v0.6 (§2.6–2.10). После дедлайна закрытие использует ту же write-транзакцию SQLite и обработку BUSY, что приём бюллетеней (`src/db/write-transaction.ts`). Уже принимаемая транзакция завершается перед подсчётом; закрытый снимок запрещает новые записи даже при ошибочном изменении расписания. Повтор принятого запроса бюллетеня может вернуть прежнюю квитанцию без новой записи.

Сначала фиксируются последняя отправленная версия в пределах тура, действующие назначения, mustVoteRoundOne и сохранённое освобождение. Черновики не учитываются. Список непроголосовавших обязанных определяется целиком до снятий. Все их работы первого тура во всех группах снимаются в `story_rounds` с кодом `not-voted-first-round` и временем; тексты, участия, назначения, бюллетени и позиции сохраняются. Освобождение после этих снятий не пересчитывается. Если не осталось работ либо остался единственный автор, конкурс становится failed без победителей/финалистов.

Активные работы получают 10/6/4/3/2/1 баллов за исходные позиции 1–6. Снятая позиция теряет баллы; другие не сдвигаются, отправка остаётся действующей. Сравнение: сумма, количества мест с первого по шестое по убыванию, затем длина по убыванию. Неизвестные или несопоставимые сохранённые длины блокируют успешный подсчёт без частичных изменений; автоматического пересчёта текста нет. ID/название/дата не разрешают равенство. Места плотные: 1,2,2,3.

Квота q=floor(F/G) одинакова для исходных G групп, включая опустевшие. Граница — q-я работа, затем добавляются все полностью равные ей. При недоборе проходят все оставшиеся, без передачи остатка/неиспользованной квоты. Поэтому финал может превысить F только вследствие равенства. При одной группе конкурс завершается без финалистов и без раскрытия авторства. При нескольких группах этап пока остаётся round-one с явным закрытым снимком: публично видны результаты и состав финала, но группа/назначения финального голосования не создаются и тур не запускается автоматически.

`first_round_closures` (миграция 0005) хранит неизменяемый приватный JSON-снимок: исходные работы/длины/статусы/авторские связи, принятые бюллетени с позициями и временем, зафиксированные обязанности/освобождения, список снятий, правила/квоту/расписание, результаты. Он нужен для проверки и никогда не передаётся браузеру целиком. `results-queries.ts` выдаёт строгие публичные поля только после появления снимка; до этого промежуточных сумм нет. Нет команды перезаписи. Противоречивая история (уже записанные результаты без снимка, история финала, неверная структура отправленного бюллетеня) блокирует операцию.

На странице конкурса — таблицы первого тура: место, название, баллы, совместное место, выход в финал и безопасная причина снятия. Тексты снятых работ по-прежнему не открываются; имена авторов, email и чужие бюллетени не выдаются. В кабинете отдельно показаны свои результаты и замороженный статус выполнения голосования. Историческая аналогия разделённой награды приведена в ТЗ и пояснении таблицы со ссылкой на NobelPrize.org; она не приписывает Нобелевской премии нашу систему баллов.

Воспроизводимый сценарий:

```bash
nvm use
npm ci
npm run db:migrate
NODE_ENV=development npm run db:demo-closure
NODE_ENV=development npm run contest:close-first-round -- demo-first-round-results
# Повтор возвращает ровно сохранённый результат:
NODE_ENV=development npm run contest:close-first-round -- demo-first-round-results
npm run dev
```

Обе команды изменения данных разрешены только в development; закрытие дополнительно требует isDemo и прошедший дедлайн. Сценарий отдельный, пользовательские конкурсы не меняет; повторный seed сохраняет состояние/сроки. Адрес `/contests/demo-first-round-results#round-one-results`. В группе 1 ожидаются 24/22/22/12 баллов и места 1/2/2/3; две работы непроголосовавшего автора в разных группах снимаются. Квота 2, но из группы 1 проходят три по равенству; из группы 2 — одна без компенсации недобора; пять равных работ освобождённого автора группы 3 проходят совместно. Всего девять финалистов при F=6 — следствие согласованного расширения по равенству, без минимального порога баллов.

Для своего кабинета восстановите доступ через development-почту к `demo-first-round-results-5@grelqa.example` (не проголосовал, две снятые работы) или `demo-first-round-results-7@grelqa.example` (освобождён). Пароли случайны/неизвестны. Письма, как прежде, сохраняются вне public/Git. Проверьте таблицы в анонимном окне, отсутствие авторства и чужих голосов; затем кабинет. Мобильная таблица прокручивается горизонтально.

После build: `npm run test:closure` проверяет заранее рассчитанные суммы, критерии/полное равенство, dense-места, отсечение квоты, игнорирование черновиков, действующую последнюю версию, снятия без сдвига позиций, все работы автора в разных группах, освобождение, failed, единственный тур, повторные/межпроцессные запуски, сериализацию с принимаемой записью, откат и приватность HTML/RSC. Остальные проверки, включая `test:voting` и `test:voting:browser`, также обязательны.

Позднейшее уточнение: финал с единственным автором после отбора запускается с освобождением автора от голосования. При снятии всех собственных финальных работ право и обязанность голосовать прекращаются. Публикация бюллетеней/авторства и окончательный подсчёт остаются отдельными шагами.

### Литературный демонабор

Основные три конкурса и рассказы используют оригинальную гонзо-сатиру: «Телеграммы из зоны здравого смысла», «Хроники муниципального апокалипсиса», «Пресс-карта на край света». Развёрнутый рассказ «Бензин для муниципального апокалипсиса» — около шести тысяч знаков; два других — самостоятельные короткие репортажи. Источники: scripts/demo-contests.ts и scripts/demo-stories.ts. Тексты вымышлены, без цитирования реальных авторов.

Для существующей development-базы есть явное обновление только базовых демозаписей:

```bash
NODE_ENV=development npm run db:refresh-demo-copy
```

Команда транзакционна и повторяема. Она проверяет фиксированные ID/slug/isDemo, организатора, владельцев трёх деморассказов и отсутствие неизменяемых снимков формирования/закрытия; при несовпадении откатывается с пояснением. Другие рассказы, в том числе пользовательские в демоконкурсах, не затрагиваются. Даты, этапы, анонимность, группы и бюллетени сохраняются; скрытая тема остаётся скрытой. Обычный db:seed по-прежнему только вставляет недостающие записи. Технические сценарии групп/голосования/итогов сохраняют свои зафиксированные тексты и данные, чтобы не подменять историю. ZIP обновится по хешу содержимого при следующем скачивании.

## Финальное голосование

Принятые правила — §2.9.1 ТЗ v0.8. `/contests/[slug]/final-ballot` использует тот же редактор, но отдельные `round=2` черновик, действующую отправленную версию, ревизию и квитанции запросов. Один подтверждённый автор финалистов — один бюллетень, даже при нескольких своих работах. Список берётся из `first_round_closures`, а не из участия в первом туре/флага finalist. Выбираются только доступные чужие финальные работы из всех прежних групп. Количество 6/все 1–5/освобождение при нуле, повторная отправка, снятые позиции и отдельный черновик работают как в первом туре. Отправленный вариант не меняется от сохранения черновика или снятия работы.

Подготовка финала атомарно создаёт общую группу round=2 и строки story_rounds только для прошедших работ, фиксирует допуск авторов и SHA-256 исходного результата в приватном final_rounds. Размер группы — весь зафиксированный состав, включая расширение по равенству, без обрезания до F. Назначения, баллы, места, освобождения и бюллетени первого тура не переписываются. Повтор подготовки возвращает тот же снимок. Группа/этап round-two создаются отдельной development-командой, без публичного переключателя:

```bash
nvm use
npm ci
npm run db:migrate
NODE_ENV=development npm run db:demo-final
# Для выбранного уже закрытого многогруппового демоконкурса:
NODE_ENV=development npm run contest:prepare-final -- demo-final-voting
npm run dev
```

Обе команды только development; подготовка дополнительно требует isDemo, успешный многогрупповой результат первого тура, отдельную дату финала и ещё не прошедший endsAt. Сам приём дополнительно проверяет stage=round-two и roundTwoStartAt <= доверенное receivedAt < endsAt. Подготовка до запланированного старта не открывает голосование раньше времени. На дедлайне и после него любые новые изменения запрещены, просмотр своих версий остаётся. Работающий финал защищён тем же механизмом транзакций, CAS/idempotency, CSRF, rate-limit и no-store, что первый тур. Тело запроса выбирает только round=1/2, но автор, допуск и финальная группа определяются сервером.

Миграция 0006 добавляет final_rounds и поля освобождения второго тура. Draft CHECK расширен до 1/2; ключ ballot_requests дополнен round. Существующие таблицы draft/requests копируются с данными, все прежние квитанции получают round=1 без изменения хеша/ответа. Старые хеши первого тура сохраняют прежний формат. Никакого db:push/reset и переноса голосов между турами нет. Проверка обновления заполненной базы включена в test:final-voting.

Ссылки доступны из кабинета и страницы конкурса. Читать финальные работы можно без входа, для голосования нужен допуск автора финалиста и подтверждённый email. На финальном рассказе «Добавить в мой бюллетень» сохраняет round=2 и ведёт на финальную страницу. ZIP финальной группы содержит только доступные финальные тексты; архив конкурса по-прежнему включает разрешённые рассказы обоих туров с согласованными папками. RSS/Atom продолжают отдавать только объявления. Бюллетени, авторские связи и суммы финала не добавляются в публичные DTO/архивы/ленты; наступление дедлайна не раскрывает авторов. Для организатора coordinatorVotingStatuses(token,slug,2) возвращает только статусы финального голосования.

Оба первоначально открытых вопроса решены пользователем. После снятия последней своей финальной работы прекращаются право и обязанность голосовать: сервер запрещает новые изменения, кабинет и бюллетень показывают причину, ранее сохранённые версии остаются для просмотра. Это не «освобождение»: отдельный roundTwoRightsEndedAt сохраняет факт прекращения, mustVoteRoundTwo=false, поля нулевого выбора очищаются. Автоматического восстановления нет. Финал, куда прошли работы только одного автора, запускается; у автора сохраняются работы и действует освобождение из-за отсутствия чужого выбора, без пустого отправленного бюллетеня. Проверка failed первого тура до отбора не изменена. Окончательный подсчёт, снятия за неголосование, победители и раскрытие авторства этим уточнением не добавляются.

Демо `/contests/demo-final-voting`: девять финальных работ пяти авторов из трёх первых групп, срок около семи дней от первоначального создания. Скрипт не меняет пользовательские конкурсы, не продлевает существующие сроки и не перезаписывает результаты. Восстановите через локальную development-почту доступ `demo-final-voting-1@grelqa.example` (одна работа, выбор шести чужих) или `demo-final-voting-7@grelqa.example` (пять своих, выбор всех четырёх чужих). `demo-final-voting-4@grelqa.example` не прошёл в финал и может только читать. Случайные пароли не известны; пути писем показываются в терминале, как ранее.

Ручная проверка: кабинет → «Мой финальный бюллетень», сохраните две работы из разных прежних групп, переставьте кнопками/drag и обновите страницу. Дополните выбор и отправьте; сохраните другой неполный черновик и убедитесь, что отправленная версия осталась. На финальном рассказе добавьте работу в черновик; первый бюллетень и итоги не меняются. Проверьте вторую вкладку и понятный конфликт ревизий. В анонимном окне проверьте чтение и ZIP без авторства, а с не прошедшим участником — отсутствие отправки. Реальные браузерные элементы, клавиатура/перетаскивание/мобильная ширина, добавление из чтения и открытая до дедлайна форма проверены Chromium.

Проверки после build: `npm run test:final-voting`, `CHROMIUM_PATH=/snap/bin/chromium npm run test:final-voting:browser`. Обе используют отдельные временные базу/почту/кэш. Сохраняются все прежние check/build/test:db/pages/auth/submissions/grouping/exports/feeds/voting/closure и test:voting:browser.


Миграция 0007 добавляет roundTwoRightsEndedAt и применяет прекращение права к уже подготовленным финалам, в том числе со старым admission.withdrawalRights=unresolved: используются сохранённые участники/работы финала и факт отсутствия своих неснятых работ. Снимки допуска, первый тур, черновики, отправленные версии и квитанции не переписываются. Для новых финалов снимок фиксирует revoke; историческое поле старого снимка больше не является переключателем текущего правила. Снятие последней работы и обновление участия выполняются одной транзакцией. Нулевой чужой выбор после дедлайна по-прежнему не пересчитывается, но факт прекращения права по уже совершённым снятиям сохраняется. Проверки обновления заполненной версии 0006 и одноавторского финала включены в test:final-voting.
